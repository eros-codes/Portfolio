What it is

Reservation is a table booking system. It was built for a café called Roof, but nothing in it is tied to one venue: the halls, the tables and the rules all come from data.

It was built by two people. A teammate built the front end, including the floor plan. I built the back end: the API, the data model, the availability and booking engine, payments, SMS codes and admin roles.

  • You book a time, not a seat. Here you pick your exact table on the real floor plan.
  • Changing the layout means changing code. Every table and every chair is edited from the admin panel.
  • Two people can book the same table. One transaction at a time makes that impossible.

A seat, not a slot

Pick a day, a party size and a time, and the tables that fit light up on the floor plan. Each table has its own range: a six-seat table can also take a group of five, but not two. A table that fits exactly glows darker than one with seats to spare.

If no single table is right, connected tables are combined for you. Whatever you choose is held for ten minutes while you pay, and every booking leaves fifteen minutes free for the table to be cleared.

The café is data

Nothing about the layout is written in code. From the admin panel, every table can be moved, turned and resized, its chairs added or removed one by one, its shape changed, and its seats, minimum and maximum set by hand. Which tables may be joined is set there too.

Access follows roles: owners and managers can change the floor, while reception can only look at it.

No table twice

When two guests tap the same table at the same moment, both requests reach the server together. Checking that the table is free and creating the hold happen inside one serializable transaction, so only one can win. The other is told plainly and asked to pick again.

The price is never taken from the request. It is read from the server's settings, so it cannot be changed on the way.
