What it is

Rivo is a real-time chat app. The server (Express and Socket.IO on Node.js) and the app (React) are both written in TypeScript and read one shared contract, so a conversation updates the instant a message is sent, and everything is kept in PostgreSQL through Prisma.

It was built to fix five things ordinary messengers get wrong.

  • Every chat is treated the same. Rivo keeps a chat up front only until its last message is seen.
  • Every message is permanent and instant. Rivo adds messages that open once, or open later.
  • Archived chats never really leave. In Rivo, an archived chat disappears from the main screen.
  • A copied database means copied conversations. Every message is encrypted with its own key; no plain text is stored.
  • A dropped connection drops messages. Rivo catches up on what it missed and sends what you wrote, once.

Chats that sort themselves

Most messengers show every conversation the same way: one long list, ordered by the last message. The friend you talk to every day sits in the same list as someone you have not heard from in a year, and you do the sorting in your head.

Rivo does it for you, with one rule: a conversation stays in Active chats as long as its last message has not been seen. A message waiting for you keeps it there, and so does one of yours they have not opened yet. Once the last message is seen and nobody replies, the conversation is over, and it moves to Contacts on its own. A new message brings it straight back.

Messages and chats with their own rules

A normal message is permanent and arrives the moment it is sent. Sometimes both are wrong: a password should not stay in a chat history forever, and a birthday note should not arrive a week early. And in most apps, an archived chat is still on your main screen, just inside a folder.

A database that reveals nothing

If a chat app's database is copied, the conversations in it usually go with it. Rivo uses envelope encryption: every message is locked with its own random key, and that key is locked again with the server's key. The database holds no plain text at all, not even inside a reply's quote or a forward.

The server's keys can be kept in HashiCorp Vault instead of on its disk. Moving to a new key re-wraps each message's own key without decrypting a single message, saves every row before changing it, and leaves a message alone if it is edited mid-way.

  1. 1

    A message is sent

    The server receives the plain text over the socket. It exists unencrypted only in memory, for as long as this request lasts.

  2. 2

    Its own key encrypts it

    A fresh 256-bit key, made for this message alone, encrypts it with AES-256-GCM, which also seals it against tampering.

  3. 3

    The server's key wraps it

    That key is encrypted in turn with the server's key, which is named (v1, v2) and loaded from Vault or the environment when the server starts.

  4. 4

    Only locked data is saved

    PostgreSQL stores the ciphertext, the wrapped key and the name of the key that wrapped it. Reading a message runs the same steps in reverse.

Nothing lost when the connection drops

A phone on a train loses its connection without saying so, and only notices when it wakes. So Rivo does not start from the moment it noticed: when it reconnects, it asks the server for everything that changed since it last heard from it, minus 30 seconds. An edit, a deletion or a message from the gap still arrives. Every message carries updatedAt, so a late event never overwrites newer data, and a deleted message cannot come back.

What you write goes into a queue first and shows at once. The queue is saved in the browser, so even a refresh does not lose it, and it is sent in order when the connection returns. Each message carries a random clientId, unique per sender in the database: if an answer is lost and the app sends again, the server returns the message it already has instead of storing a second one.

Built to be trusted

  • One contract. The app and the server read the same types and the same zod schemas from shared/. Every input is checked against its schema before anything else, and renaming a field breaks the type check on both sides at once.
  • Real sessions. Each sign-in is a row in the database, so logging out a device takes effect at once, and a password change signs out every other device but this one. CSRF uses a signed token derived from the session.
  • Quotes that cannot be forged. A reply or a forward sends only a message id; the server builds the quote from the original, so nobody can quote words that were never written.
  • "Contacts only" means contacts. Being added by someone no longer makes you their contact, which used to show your photo and last seen to anyone who added you.
  • Limits that hit attackers, not users. Sign-in limits count only failed attempts, per account and per IP (an IPv6 address by its /56 network), and the email code allows five guesses even when they arrive at once.
  • No account leaks. Sign-up and password reset never reveal whether an email has an account, not even through how long they take.
  • Closed doors. Push messages only go to the browsers' own push services, and the email check cannot be stalled by a 60,000-character address.
  • Tested where it runs. Unit, API and browser tests (113 in all) run in GitHub Actions on every push, the browser tests in Chromium, Firefox and WebKit. A load test measures how fast messages arrive with many people chatting at once.
